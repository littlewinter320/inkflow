## 二、Writer 灵感分身（零依据构思不再被审核机制卡住）

### 2.1 背景与目标

用户指出 Writer 的内部审核机制过于严格：当从一个想法“从 0 开始”、或暂时没有正史、规划等依据可查时，不应强行走证据核验流程，而应直接进入创意构思。需要一个独立的"小 Writer 分身"来执行这一类需求。

### 2.2 完成的修改

#### （1）新增输出模型 `CreativeBrainstorm`（schemas.py，第 57-60 行）

只定义一个字段 `reply`（1~6000 字），承载面向用户的创意提案文本。刻意不定义章节结构、审查分数等正式写作产物字段，从数据模型上保证"只出提案、不出正文"。

#### （2）新增系统提示词 `WRITER_IDEATE_SYSTEM`（prompts.py，第 10-22 行）

明确灵感和正式 Writer 的分工：
- 灵感分身只在"用户没有依据、或明确想要天马行空的点子"时出手；
- 不做证据核验、不引用正史、不产出正文章节，输出的是"创意提案"；
- 提案不会被自动接受、不会写入正史，用户选中后才进入正式流程；
- 创作要求：大胆、具体、可感，多给彼此不同的方向，尊重用户已明说的偏好。

#### （3）新增引擎方法 `Engine.brainstorm()`（engine.py，第 85-115 行）

实现要点：
- 打开项目并新建 Trace（trace 类型 `writer-brainstorm`）；
- 把 Context Packet 转成 Markdown 后**截断到末尾 6000 字符**，仅作为背景参考，明确"不需要核验"；
- 调用模型：`effort="low"`、`max_tokens=2400`、`thinking=False`、`agent_role="writer"`、`timeout_seconds` 取设置与 120 秒的较小值；
- 成功后记录模型 Trace，摘要固定为"创意提案已生成，未写入任何正文或正史"；
- 返回 `reply`、`model`、`next_action`（提示用户选中方向后进入正式规划）、`trace_id`。

#### （4）路由白名单接入（coordinator.py、schemas.py、terminal_session.py）

- `coordinator.py` 的 `_WORKFLOWS` 新增条目：
  `"ideate": (("writer", "idea.brainstorm", "", "创意提案"),)`——只有巧一个 Writer 步骤的创作流程；
- `schemas.py` 的 `TerminalAction` 字面量新增 `"ideate"`；
- `terminal_session.py` 路由提示词新增语义说明（第 41 行）：用户"要从零构思、想要灵感、点子或天马行空的提案，且当前没有正史或规划依据可查"时 → `ideate`；"用户明确要求出点子时 `authorization=approved`"。
- `terminal_session.py` 执行分支（第 252-259 行）：
  - `authorization != "approved"` 时返回 gate 文案"想让我出点子的话，直接说就行，例如"帮我想几个故事点子""，不执行；
  - `approved` 时调用 `engine.brainstorm(project.root, text, packet)` 返回提案。

#### （5）预编译检查

该分支不调用 Memory Keeper、不进入正史，符合"用户只要草稿不自动验收"的产品边界；空步骤之外只有记者步骤，不会改写任何基准文档。

## 三、Coordinator 软化 + 墨宝人设

### 3.1 背景与目标

用户反馈 Coordinator 过于强硬：问候、闲聊被当成"跑题/追求效率"，甚至"我要怎么称呼你"这类问题也没有被正常回应。要求：Coordinator 是"聊天型 Agent 与工作型 Agent 之间的中间 Agent"，本职工作是把控工作流安排，专业的事交给专业 Agent，对不同需求分辨回复方式；同时整体代入墨宝（墨滴小精灵）设定，有自己的个性和说话方式。

### 3.2 完成的修改

#### （1）新增 `MOBAO_PERSONA`（prompts.py，第 1-7 行）

墨宝人设要点：
- 墨滴小精灵，说话亲切、带一点俏皮但懂分寸；
- 闲聊时像朋友：接住寒暄、玩笑、情绪和日常问题，不端着、不卖萌没完没了；
- 工作时简洁清晰：涉及创作任务换成利落口吻；
- 可以被轻轻带一句创作邀请，但绝不强推、不说教、不催干活；
- 知道自己背后还有 Writer、Reviewer、Memory Keeper，专业的事转交、不冒充；
- 回复保持在策略短（一般不超过三句话），不输出原始思维链。

#### （2）路由提示词注入墨宝口吻（terminal_session.py，第 92 行）

`TERMINAL_ROUTER_SYSTEM` 在文件末尾追加：
"墨宝口吻（适用于你写出的所有 conversation_reply）：\n" + MOBAO_PERSONA
即：路由与回复仍由 Coordinator 负责，但对用户说话时全部以墨宝的身份进行。

#### （3）新增 `chat` 动作与语义（terminal_session.py、schemas.py、coordinator.py）

- 路由提示词第 40 行新增 `chat` 语义：寒暄、闲聊、情绪表达、与创作无关的日常提问（如"晚上好""我该怎么称呼你"）→ `chat`，`conversation_reply` 以墨宝口吻直接、完整回应，**不进入工作流、不说跑题、不催促干活**；
- 轻量会话规则（第 79-81 行）：闲聊优先 `chat`；只有讨论创作话题才是 `discuss`；只有明确要具体点子才是 `ideate`；不要把闲聊判定为跑题，也不一味追求效率；
- 执行分支（第 246-251 行）：`chat` 直接返回 `intent.conversation_reply`（路由模型已按墨宝口吻写完），空回复时兜底"我在呢。想聊点什么，或者继续你的故事都可以。"；
- `coordinator.py`：`_WORKFLOWS["chat"] = ()` 空流程（不派工）；`_model_call_budget` 中 `chat`/`discuss` 各计 1 次模型调用。

## 四、每条对话消息底部：复制 / 回退 / 重新运行

### 4.1 背景与目标

用户要求：每个对话的最底部要有"复制"和"回退"两个功能（而不是把回退集中放在一个 UI 上）；用户消息可编辑后重新运行，或直接再次重新运行（“重新运行”需要建立在回退功能之上）。

### 4.2 完成的修改

#### （1）App.tsx 新增三个处理函数（第 700-734 行）

- `copyMessageText`：`navigator.clipboard.writeText(message.text)` 复制该条文字，成功/失败分别提示。
- `rollbackToMessage`：
  - 找到消息索引后按角色分两种截断；
  - user 消息：`messages.slice(0, index)` 截断到位，原文放回输入框（可编辑后重发）；
  - assistant 消息：`messages.slice(0, index + 1)` 保留到该条为止，清掉其后消息；
  - 同时清空待回答问题列表 `setPendingQuestions([])`。
  - 注释明确：只截断前端消息列表，不改动 DIALOGUE.md、正史或 SQLite。
- `rerunMessage`：busy 时直接 return；截断该 user 消息之后所有消息，清空待回答问题，把原文交给 `sendChat(undefined, target.text)` 原样重发。

#### （2）消息操作栏渲染（App.tsx，第 1123-1132 行）

每条消息（welcome 除外）底部渲染操作栏：
- "复制"（title：复制这条消息的文字）
- "回退"（title 按角色区分：user≈原文放回输入框可修改后重发；assistant≈回退到这条回复之后）
- 仅 user 消息额外显示"重新运行"（busy 时 disabled）
- 原有朗读按钮保留在同一操作栏

#### （3）样式（styles.css，第 825-832 行）

- 移除 `.message > div` 的 `padding-right: 28px` 与 `.message-speak` 的绝对定位；
- 新增 `.message-actions`：默认透明（opacity 0），消息 hover 或焦点进入时显现，触屏设备（`@media (hover: none)`）常显；
- `.message-action`：小字透明底按钮，hover 时加深背景呈现。

## 五、语音输入三处修复

### 5.1 背景与目标

用户反馈三点：① 语音识别会原样输出一段带 `<|yue|>` 等标记的 JSON（lang / emotion / event / text / timestamps / tokens / words 全字段），要求直接形成自然语言；② 语音停止时只生成在输入框里、不要直接发送；③ 最好是"边听边输出"，可接受一定延迟。

### 5.2 完成的修改

#### （1）识别结果从 JSON 解包为纯文本（agent/src/inkflow/voice.py，第 988-1003 行）

- `raw = str(getattr(stream, "result", "") or "")`；
- 当原始结果以 `{` 开头时尝试 `json.loads`，若为 dict 则取 `payload.get("text")`；解析失败则保留原文；
- 再统一用 `re.sub(r"<\|[^|]*\|>", "", text)` 去掉 `<|yue|>`、`<|NEUTRAL|>`、`<|Speech|>` 等内联标记；
- 清洗后为空则抛"没有识别到清晰的普通话内容…"。
- 由此，输入框只会收到自然语言文本，不再出现 JSON 串。

#### （2）快照接口 `LocalWavRecorder.snapshot()`（desktop/src/voiceRecording.ts，第 50-60 行）

- 不停止录音，把当前已累计的 PCM 片段复制出来，编码成 WAV（`encodeMonoWav`）构成的 `Uint8Array`；
- 依赖 JS 单线程特性：编码期间 `onaudioprocess` 不会并发写入 `chunks`，读安全；
- 与 `stop()` 的区别：stop 会断开音频源、停流、关 AudioContext 并返回全长音频；snapshot 只是"当前时刻的胶片"，录音可继续。

#### （3）边听边出字 + 停止只入框（App.tsx）

- 新增两个 ref：`voiceLiveTimerRef`（定时器句柄）、`voiceLiveBusyRef`（防重入锁）；
- 录音开始（第 852-857 行）：启动 `LocalWavRecorder` 后 `window.setInterval(…, 2500)` 每 2.5 秒调用一次 `transcribeLiveSnapshot`；
- `transcribeLiveSnapshot`（第 753-769 行）：用 `recorder.snapshot()` 取快照，跳过空数据（≤44 字节的 WAV 头），经 `window.inkflow.saveVoiceRecording(…, "wav")` 落临时文件后调 `voice.transcribe`，把识别文本 `setChatInput(result.text)` 实时填进输入框；任一环节失败都静默跳过（不打断录音）；
- 停止录音（第 823-845 行）：先清掉定时器，再做一次完整 `stop()` + 转写，结果只 `setChatInput`；仅当设置 `voice_auto_send` 为开时才自动发送，默认关闭 ⇒ 停止后只生成在输入框，由用户决定是否发送；
- 打开录音时提示语更新为"正在听普通话，识别结果会实时出现在输入框；再点一次麦克风停止"。

#### （4）设置项（config.py，第 171-172、289-290 行）

`voice_auto_read`、`voice_auto_send` 默认值均为 `False`，与前端默认状态一致；语音设置界面保留"识别后直接发送 <small>关闭时只填入输入框</small>"开关。

## 六、输入区智能提示词

### 6.1 背景与目标

用户要求把固定快捷提示词改为"预测用户要做的提示词"：需实时结合每个对话调整，而不是固定文案；并可在设置里取消该功能。

### 6.2 完成的修改

#### （1）输出模型（schemas.py，第 63-73 行）

- `SuggestedPrompt`：`label`（按钮文字，1~24 字）+ `prompt`（完整可发送中文语句，1~200 字）；
- `SuggestedPrompts`：`suggestions` 1~5 条。

#### （2）预测系统提示词 `ASSISTANT_SUGGEST_SYSTEM`（prompts.py，第 25-33 行）

- label 不超过 12 字、prompt 是可直接发送的中文自然语句；
- 必须贴合当前项目阶段与最近对话（未规划→规划类；有草稿→审查/修订类；有批次→接收类；刚聊完话题→自然下一步）；
- 只预测墨流真实支持的事（讨论/规划/写草稿/审查/修订/验收/批次/回退/状态/闲聊），不预测越权操作；
- 语气自然，不堆命令词、不用"请"开头客套。

#### （3）后端方法 `assistant.suggest`（app_server.py，第 238-278 行）

- 入参：`workspace_root` / `project_root`、`recent_messages`（取最近 6 条，每条截断 400 字）；
- 组装 Context：项目状态摘要（`_project_status_summary`：最近已接受章节、草稿章节、当前篇章范围）+ 最近对话；
- 调用模型：`effort="low"`、`max_tokens=600`、`thinking=False`、`timeout_seconds` 取设置与 45 秒较小值、`agent_role="coordinator"`；
- 任一异常静默回退 `_local_suggested_prompts`，**绝不抛错打断对话主流程**；返回 `{suggestions, model, fallback}`。

#### （4）本地规则兜底 `_local_suggested_prompts`（app_server.py，第 1396-1440 行）

- 无项目：想想点子、查看状态；
- 有项目但无规划：规划当前篇章、想想点子；
- 有规划且有草稿：审查当前章、验收进正史（用草稿章节号）；
- 有规划无草稿：写当前章（先不要审查）；
- 无项目始终有"先问我"条目；结果截取前 5 条。

#### （5）前端接入（App.tsx）

- 状态：`suggestedPrompts`（默认值 `defaultSuggestedPrompts` 5 条固定引导文案兜底）、`suggestedPromptsEnabled` 偏好（默认 true，读取 localStorage 时 `!== false` 视为开）；
- 每轮对话结束后（`sendChat` 的 finally）调用 `refreshSuggestedPrompts([user, assistant])` 刷新，失败静默保留当前建议；
- 渲染（第 1108-1114 行）：开启时在输入区上方显示 `.quick-row` 按钮行，点击直接发送对应 prompt；
- 设置（第 1887 行）：创作分类新增"智能提示词"开关，关闭即隐藏整行按钮、且不再发起预测调用（避免费用与 token 消耗），备注中说明"每轮对话后会调用一次模型预测"。

## 九、未完成项与风险

1. **智能提示词成本**：每轮对话结束后会多一次低成本模型调用（effort=low）；已提供设置开关，关闭后不再调用。
2. **回退边界**：消息回退是纯前端 UI 操作，不回滚 DIALOGUE.md 或正史；若用户希望"回退同时改写后台对话记录"需另行设计（涉及对话历史写入策略变更）。
3. **语音延迟**：边听边出的 2.5 秒间隔是取"可接受一定延迟"的折中；录音环境噪声大时实时识别可能间歇无输出（静默跳过，停止后的完整转写兜底）。
4. **发布流程**：尚未打包安装包、未推 GitHub、未建 Release；`voice_auto_send` 等新设置项的存储随既有 `Settings.from_env` 机制，无格式变更。
