# 墨流 0.3 调研依据与设计取舍

> 记录日期：2026-09-08。本文是 0.3 的内部依据账本；只记录实际影响设计的来源和结论，不把资料链接数量当成质量。

## 结论摘要

墨流不需要继续增加正式小说 Agent。当前主要问题是上下文层级、规划粒度、用户确认方式和重复写作方法没有被稳定封装。0.3 因此保持 Writer、Reviewer、Memory Keeper 三个角色，把确定性工作留给 Python，把重复方法做成技能，把真正影响成品的未知项交给结构化提问。

## 长篇记忆与 Token

OpenViking 把上下文分为 L0 摘要、L1 概览与 L2 详情，并采用分层检索和渐进加载。这支持墨流“最近章节全文 + 相关旧章摘要 + 正史事实索引”的做法，而不是把所有文件平铺进每次调用。[OpenViking 上下文层级](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/03-context-layers.md)、[OpenViking 架构](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/01-architecture.md)

SQLite FTS5 提供 BM25 排序，但 0.3 暂时没有必要迁移数据库或新增索引表。当前章节摘要数量可用纯 Python 的本地 BM25 风格排序解决；当真实项目规模证明需要全文检索时，再评估 FTS5。[SQLite FTS5 官方文档](https://www.sqlite.org/fts5.html)

DeepSeek 的上下文缓存以相同前缀命中为核心，并默认启用。墨流应保持系统提示与硬约束顺序稳定，把高变化的章节任务放在后面；同时不能把“上下文上限”误解成每次都应填满。[DeepSeek 上下文缓存官方说明](https://api-docs.deepseek.com/guides/kv_cache/)

## 长篇规划与节奏

CONCOCT 指出长篇生成常见的问题是重要事件被一句带过，而次要事件被过度展开；它用分层大纲和事件具体程度控制节奏。墨流据此增加“重要节点场景化、连接段压缩”的动态技法，并在章节卡中明确不可逆变化。[Improving Pacing in Long-Form Story Planning](https://openreview.net/pdf?id=KUSzNKRI2g)

DOME 使用动态分层大纲并在生成过程中检索相关记忆，说明远期规划应保留粗粒度、临近篇章才逐步细化，同时让已写结果回流后续规划。墨流继续采用全书—卷—篇章—章节卡四级滚动规划。[Generating Long-form Story Using Dynamic Hierarchical Outline and Memory-Enhancement](https://openreview.net/pdf?id=ZCCydvipRt)

## 人物心理与沉浸

叙事研究把时间事件、有目标的行动者和因果序列视为故事的重要结构，并指出可信感、人物认同和情绪参与与沉浸相关。墨流把这些结论转成“人物所知/所怕/所求—选择—后果”的写法，不把心理学术语直接贴成角色诊断。[Stories in Action](https://pmc.ncbi.nlm.nih.gov/articles/PMC10173355/)、[The Power of the Picture](https://pmc.ncbi.nlm.nih.gov/articles/PMC4675523/)

人物认同与叙事沉浸并不等同：读者可以从角色视角体验目标、情绪和知识，也可以把角色视为外部对象。写作技能因此强调稳定视角和人物知识边界，同时允许读者与角色之间存在信息差。[Adult attachment and engagement with fictional characters](https://pmc.ncbi.nlm.nih.gov/articles/PMC8419286/)

## 钩子、悬念与伏笔

研究区分面向未来结果的 suspense、面向过去原因的 curiosity，以及迫使读者重构预测的 surprise。墨流不再把所有章末问题都叫同一种悬念，而是在章节卡中轮换危险、揭示、决定、逆转、代价和余韵。[Presence, flow, and narrative absorption](https://pmc.ncbi.nlm.nih.gov/articles/PMC10446082/)

信息缺口只有在读者知道“自己缺什么”时才容易产生具体求知动机；过大或完全无背景的缺口反而难以形成有效好奇。墨流据此要求 hook_question 能被读者复述，并已由人物的下一步行动连接到后文。[Information seeking, curiosity and attention](https://pmc.ncbi.nlm.nih.gov/articles/PMC4193662/)、[Boredom and curiosity](https://pmc.ncbi.nlm.nih.gov/articles/PMC11669060/)

EACL 2024 的悬念故事工作使用迭代规划而非只在成稿尾部临时加悬念。墨流因此把钩子与伏笔生命周期放进四级规划和章节卡，再由 Writer 落地、Reviewer 核对。[Creating Suspenseful Stories](https://aclanthology.org/2024.eacl-long.147/)

## 提问交互

人机协作的可靠模式是暂停当前运行、保存可恢复状态、收集结构化回答后再继续，而不是让 Agent 在等待时继续猜。墨流 0.3 的提问卡先结束本轮路由，用户回答后以自然语言继续会话。[Stately Agent human-in-the-loop](https://github.com/statelyai/agent/blob/next/docs/human-in-the-loop.md)、[OpenAI Agents SDK human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)

Windows 控件指南建议互斥选择使用单选，多项选择使用复选，并让用户在选择前看见所有选项。墨流问题结构因此明确区分 single/multiple，并始终在最后追加自由填写的“其他”。[Microsoft 单选按钮指南](https://learn.microsoft.com/windows/apps/design/controls/radio-button)

## VS Code

VS Code 官方建议 Webview 只在普通工作台 API 不足以表达功能时使用，并保持主题、键盘和可访问性；墨流只为集中式创作主控使用一个 Webview，提问则优先使用原生 Quick Pick。发布包补齐 README、图标、变更记录和入门引导。[VS Code Webview 指南](https://code.visualstudio.com/api/ux-guidelines/webviews)、[VS Code UX 指南](https://code.visualstudio.com/api/ux-guidelines/overview)、[发布扩展](https://code.visualstudio.com/api/working-with-extensions/publishing-extension)

## 软件内更新

Electron Builder 的官方更新器支持 Windows NSIS、生成 `latest.yml`、下载进度和通用 HTTPS/GitHub 等发布源。墨流现有安装包就是 NSIS，因此可在不迁移小说项目的前提下加入“检查—下载—重启安装”。[electron-builder 自动更新](https://www.electron.build/docs/features/auto-update/)、[Windows 构建目标](https://www.electron.build/v26/docs/targets/)

GitHub 官方说明私密仓库 Release 资源需要具有 Contents 读取权限的令牌；只有公开资源可以匿名获取。大众客户端不能内置仓库令牌，因此私密阶段只完成更新框架，正式启用时应公开仓库、使用独立公开发布仓库，或提供通用 HTTPS 更新目录。[GitHub Release assets API](https://docs.github.com/en/rest/releases/assets)

## 采用与暂缓

- 采用：分层上下文、本地旧章摘要排序、动态技法、结构化提问、用户选择后导入的公开搜索、完整 VS Code 主控。
- 暂缓：向量数据库、第四小说 Agent、每章自动联网、付费搜索 API、自动 Marketplace 发布。
- 触发再评估：本地摘要超过数千条导致排序变慢；公开搜索页面结构变化；目标模型不支持结构化问题输出；需要多人或跨设备协作。
