# DeepSeek 输入缓存专项

目标：Writer 在正常连续创作中的输入缓存命中率达到 80% 以上，且降低实际输入计费。目标尚未由线上数据验证，不承诺每次请求达到。

## 官方机制（2026-09-22 核对）

来源：https://api-docs.deepseek.com/guides/kv_cache/

缓存默认启用，按已持久化的完整前缀单元匹配。A+B 后请求 A+C 不保证立即复用 A；服务端发现共同前缀后可持久化 A，后续 A+D 才能命中。请求边界与长文本固定间隔也会产生缓存单元。持久化需要时间，服务端为 best-effort，闲置缓存可能回收。

## 已定位与调整

- Provider 已有规范化 JSON Schema（固定键序、紧凑序列化），保留，不重复改造。
- 原 ContextPacket 把变化的输出范围放在稳定大纲之前；正文上下文也把每章变化的正史、章节卡、最近正文放在大纲之前。
- 调整为固定边界规则、长期规则、大纲/剧情细纲优先；当前事实、检索、章节卡、输出要求和本次任务随后。只改变序列化顺序，不删除当前事实、不改变权限与内容优先级。
- 新剧情细纲不按章节读取，避免每换一章就替换整段上游资料。

## 后续真实验收

分别统计 Writer 的大纲、细纲、计划、初稿、返修模式，不把不同 system/schema 的请求混成一个“已预热”序列。冷启动与稳态都报告；按 sum(hit)/(sum(hit)+sum(miss)) 加权，不能平均各次百分比。主要用计划内批量与单章任务观测，不额外制造付费预热请求。

同时看输入总量、未命中 tokens 和费用。若稳定材料天然不足总输入的 80%，继续缩减重复包装和无关动态材料；不得灌水、保留过期状态、扩大无关上下文或牺牲正文质量来凑比例。遇到材料修订、切模型、切输出契约或缓存过期，单独标记，保留总体成本统计。

## 专项复核：实现顺序与边界

2026-09-22 再次核对本地调用链 `context.py → ContextPacket.to_model_prompt → provider.generate_json → trace → _usage_overview`，并重读上述三个实际 Writer 用量记录。下面是研究结论和待实施项，不是已经达到的性能结果。

1. **稳定请求前缀（已有第一步改动，待真实写作验证）**：保持同一任务模式的 system 和 Schema 一致；正文的 A0 是固定边界规则，J 是书级规则，O 是独立大纲/剧情细纲。章节编号、当前事实、草稿、审核报告和修订指令留在后面。规则或大纲被用户修改时必须立刻使用新内容，接受重新建立缓存的成本，不能缓存旧状态。格式修复目前追加要求到原 user prompt 后面，保留这一点。
2. **缩小必要的动态输入（下一项实验）**：检查章节卡包装、重复事实和检索片段是否重复出现；只去掉可证明冗余的内容。近期正文、人物知识边界、当前有效事实不能仅为命中率被删掉。先观察真实章节输入，再决定哪些字段可以压缩，不能预先武断降低检索/记忆预算。
3. **分模式观测（统计待补充）**：现有 `_usage_overview` 正确使用 token 加权，但只按 Agent 聚合，尚未按模型和工作阶段拆分。应复用现有 events 的 `metadata.model`、`agent_role` 和 `stage` 区分初稿、返修、规划等；另标记是否发生重试。缺失缓存 usage 仍然列为未知，不能当成零命中或从总成本中抹掉。仅按 stage 还不足以证明前缀相同，材料修订也要在比较时说明。
4. **修正费用口径（待实施）**：现有 `estimated_cost` 使用全部输入乘同一个配置价格，不能直接展示缓存节省。可靠口径为 `(hit × 命中单价 + miss × 未命中单价 + output × 输出单价) / 1e6`，且必须使用对应模型、时期和币种的价格。历史日志缺少价格快照时只能标明按指定价格重算的估算，不冒充实际账单。不得写死一个所有模型通用的折扣；未知 usage/网络超时的潜在费用必须说明。
5. **用正常创作验收，不额外预热**：利用用户已安排的连续章节工作，逐次保留模型、阶段、输入/命中/未命中/输出 tokens、耗时、返修次数和字数验收结果。分别报告整批结果与相同材料版本下的连续初稿结果，不为剔除低命中数据把所有低值都叫冷启动。优先比较每个合格章节的未命中输入与总成本，避免通过增加失败重试来提高命中百分比。

## 80% 的可行性条件

若可复用前缀是 S tokens、每次变化的尾部是 D tokens，且只有该前缀可命中，则理想命中率约为 `S/(S+D)`。达到 80% 需要 `S ≥ 4D`，这只是输入结构条件，不是服务端命中保证。例如 S=8,000、D=6,000 时约为 57%；只有合理减少动态冗余才可能改善，不能靠额外填入无关设定补成 80%。返修会带入完整草稿和审核报告，天然不同于连续初稿，应独立评价。

缓存不是模型训练或回答复用，不需要下载小说、训练 Agent 或增设 Memory Keeper 来开启。也不应为了共享缓存合并 Writer/Editor 的职责与不同审核契约。本地 memoization 只能减少本地计算，不能替代 DeepSeek 服务端缓存计费；当前官方机制也没有要求调用方传 OpenAI 的 `prompt_cache_key`，不要把该字段作为 DeepSeek 命中率开关。

## 首批正文实测与后续修复

| 阶段 | 输入 tokens | 命中 tokens | 命中率 |
| --- | ---: | ---: | ---: |
| 第 1 章初稿 | 24072 | 0 | 0% |
| 第 2 章初稿 | 27721 | 21760 | 78.5% |
| 三次字数补写合计 | 11531 | 3072 | 26.6% |
| Writer 总计 | 63324 | 24832 | 39.2% |
| 第 1 章审核（含一次格式恢复） | 56714 | 2304 | 4.1% |

初稿稳定前缀已经部分生效，但仅一次连续初稿样本，不能称日常达到 80%。审核旧日志只保留两次请求的合计 usage，不能据此确定是缓存持久化延迟还是思考模式切换导致未命中。

本地修改：字数恢复改为插入段落方案、程序保留原段，避免整章重写被逐字保留规则拒绝；仍待真实运行验收，不声称已降低账单。usage 新增按模型/角色/阶段拆分；Provider 新增逐次响应 usage 与思考模式记录，以定位重试前后命中差异。新增数据不与总 usage 重复相加。未返回 usage 的超时仍是未知费用，不能宣称零成本。

当前声音契约包含按章节选取的偏好，输出契约也依赖章节卡，不能仅凭标题把它们当固定内容提前而破坏更长的前缀。下一轮先用正常生成的逐次记录定位瓶颈，不另发付费预热请求。实际 80% 目标仍未达成。
