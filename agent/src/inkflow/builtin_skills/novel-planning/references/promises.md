# 伏笔、钩子与承诺规划标准

适用：当前规划确有需要跨章追踪的问题、关系或回应。不要求每章新建条目，不让预计章号支配人物因果。

## 定义合同

- 同一thread_id代表同一承诺；下层沿用完整PromisePlan，不改名伪装新条目。
- question写读者具体想知道的问题，purpose写叙事作用。
- causal_basis说明设定、人物动机及事件为何能造成这个问题。
- trigger_conditions列出开始回应所需的可观察前提；completion_criteria列出什么结果才算真正回答。
- milestones从需要兑现的结果倒推。首次出现给细节一个当场用途；后续用新证据改变解释、人物能做的事或选择的代价；到条件满足时让人物用上它并写出结果。短线可以省去中间节点，长线可分段给部分答案。一个局部答案不能冒充整条完成。
- kind按当前Schema区分foreshadow、hook、mystery、relationship、promise、plot；短期不自动等于钩子。
- horizon区分short、arc、volume、book、open。short通常是近几章的安排，不用它限制所有题材。
- window_start与window_end只是预计章段；条件未满足时不能因到章强制兑现。开放结尾写清open_reason，不提前假定尚未决定的真相。

## 跨层分配

大纲与卷层定义长期问题和因果；近期窗口安排局部推进；章节的promise_beats引用真实thread_id，以plant、advance、payoff、delay和expected_change说明本章实质变化。下层新动作写在expected_change，不另抄一份同ID但触发条件不同的合同。

## 交给正文和审核

Writer把实际动作落在正文，公开说明只定位当前动作与有意暂缓之处。审核按真实来源核对前提、行动、代价和回应，不能把规划本身当已发生证据。memory_owner独立核验后交增量；完整触发与完成条件均有原文支持、当前正文也有实际回应结果，才可能paid。

## 失败边界

旧条目缺合同如实待核；新灵感先在允许层级形成候选，不偷偷改大纲或正史。延后不改原条件来制造完成。跨层定义不一致交原对齐工具，发布与恢复保持原版本和来源身份。
