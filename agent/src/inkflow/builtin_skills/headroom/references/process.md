# 上下文余量管理：读真实容量，保必要资料

## 开始条件

作者主动点名@headroom或要求使用上下文余量管理时，在原任务中使用。它读取当前角色设置和既有输入策略，不安装代理、不运行第三方压缩模型，不自动扩大窗口、改供应商或删硬材料。

## 1. 读取当前角色容量

输入：冻结任务、实际角色、所用模型和当前设置。
操作：执行scripts/inspect.json对应的context.inspect，读常用取材量与最大容量。
输出：真实本地容量回执；对模型只提供稳定必要数值，任务身份等留本地。
验收：工具读数不是最终完整请求计数；系统规则、Schema、历史、当前资料和必要输出空间仍由原Provider核算。
展示：用“常用取材量”“最大上下文容量”解释，不能说“命中缓存就不占容量”。

## 2. 判断哪些材料不能丢

输入：原目标、必要原文、硬要求、事实来源、可选说明与经验。
操作：保留判断所需原件和未完成交接；先排除与当前角色无关的方法和重复说明。不能为了容量省略关键反证或接受门禁。
输出：必要项、可选项和具体缺口。
验收：精简后仍能回答本次问题；检索摘要不足时回读原文，不能靠猜测填空。

## 3. 沿现有会话边界整理

输入：原持续会话、版本、材料复用状态与完整请求估算。
操作：只沿既有SessionContext自然边界处理；能复用同版材料就复用，整理无收益保留原前缀。技能不新增一种压缩或缓存执行器。
输出：原引擎实际回执。只加载本步骤的技能与相关引用，素材不用就不装入模型。
失败交接：必要材料仍装不下时交明确缺口和可行范围，不能自行提容量或偷偷多发请求。

## 4. 核收益与结束

输入：发送前估算、真实模型usage、调用次数、有效结果与未知用量。
操作：分开比较检索命中、供应商缓存和资料正确采用；缓存输入仍占上下文。字符减少仅是本地字符量，不能写成真实Token或费用节省。
输出：可证的输入、缓存、输出、耗时和结果观察；未知单列。
验收：不为刷缓存制造重复请求，不用比例掩盖输入变大、额外补救或失败产物。
取消和恢复仍沿原任务设置、预算及技能快照。自动学习保留真实观察，技能改写先交候选，不后台试跑。
