# 四 Agent 协作与记忆检索

墨流现在有四个正式 AI Agent：Coordinator、Writer、Reviewer、Memory Keeper。前三者不是“多几个聊天窗口”，而是由 Coordinator 生成结构化任务单，Novel Engine 校验角色权限和工作流后，再把同一个版本的资料交给对应 Agent。

## 完整工作流

```text
用户自然语言
→ Coordinator 理解、澄清、任务拆解、预算与调度计划
→ Novel Engine 校验预定义工作流、版本、权限和项目写锁
→ Context Builder 编译唯一 Context Packet
→ Writer 规划 / 草稿 / 定点修订
→ Reviewer 对当前版本做证据化审查
├─ patch：把证据与修订要求发回 Writer，新版本必须重审
├─ unknown / replan：交给 Coordinator 汇总缺口并询问用户
└─ pass：等待用户验收
→ Memory Keeper 只从用户验收的正文提取补丁
→ SQLite 同时提交正文与记忆 + 可恢复文件投影日志
→ Memory Keeper 向 Coordinator 发送正史同步结果
→ Coordinator 向用户汇总
```

批量生成仍严格逐章执行。第 N 章通过 Reviewer 后，Memory Keeper 会先把摘要、事实和伏笔保存为“批次临时记忆”，供第 N+1 章检索；它不是正史。集中验收时再按章节顺序逐一校验当前版本与哈希、提升临时补丁并提交正史。任何一章失败都会停在该章，不跳过继续。

桌面端的协作看板会显示任务状态、Agent 交接、审核问题、可接收批次和本地学习信号。批次只有处于 `ready_for_acceptance` 时才能由用户确认接收；接收动作仍按连续章节逐一通过 Memory Keeper，不存在“整批跳过门禁”。

## 协作消息

Agent 之间传递结构化消息，不传无来源的群聊全文。每条消息保存协作议题、运行编号、发件与收件角色、消息类型、章节、草稿版本、Context Packet、观点、证据、期望回复、状态和过期时间。单个任务最多两轮方向讨论；仍有歧义或分歧时交给 Coordinator，再由它向用户提出最小问题。

“讨论认为可行”不能代替门禁：Writer 改出新版本后，Reviewer 必须重新审查新正文；Memory Keeper 也必须在用户验收时重新核对版本和正文哈希。已验收正文完整保存在 SQLite，章节 Markdown 是可重建投影；当前版本发生中断时可由数据库正文确定性恢复。

## 共享记忆与优先级

SQLite 保存已验收正史、用户硬规则与弱偏好、当前版本协作消息、审查记录、批次临时记忆、接受/拒绝/修订学习事件和检索反馈。写权限按角色分离，协作消息与临时记忆不能直接升级为正史。

冲突优先级固定为：

```text
用户当前明确指令
> 已验收正史
> 用户长期硬规则
> 当前章节卡
> 已确认工作决定
> 用户弱偏好
> Agent 建议
> 外部作品特征
```

人工 Story Bible 与正史同时出现时会分别标注；如果冲突，以正史为准并报告，不能拼成一个“折中事实”。

## 混合 RAG

当前检索顺序为：SQLite 稳定 ID / 实体精确查询 → 本地 BM25 → 可选 BGE-M3 语义召回 → 融合去重 → 可选 BGE reranker → 一跳关系扩展 → 章节、版本和角色可见范围过滤 → 唯一 Context Packet。结果数量依据查询复杂度和候选规模自适应，不使用固定 Top K。被 Reviewer 正确引用或判定误导的来源会形成检索反馈，影响后续排序。

默认不下载模型，精确查询与 BM25 可直接工作。在设置里填写 `BAAI/bge-m3` 或 `BAAI/bge-reranker-v2-m3` 后才会启用本地语义模型；需要先安装 `pip install -e ".[rag]"`。Qdrant 是数据变大后的可重建派生索引；LightRAG 与 HippoRAG 2 仅作为内测对照，不接管 SQLite 正史。

## 上下文容量

桌面端每四秒读取一次最近 Context Packet 的容量状态。达到软预算的 90% 后，Context Builder 按固定优先级压缩外部参考、写作技巧、低排名检索结果、较早正文和人工工作资料；用户当前指令、已验收正史、长期硬规则、章节卡与输出门禁不可压缩。若硬材料本身超过最大容量，流程停止并请用户缩小范围，不静默删除。

面板会说明每段资料为何保留或可压缩，并允许用户锁定最多六条非正史工作资料。锁定资料会单独放进不可压缩区；它仍然是工作资料，不会因此变成正史。锁定过多导致硬预算不足时，系统会停下而不是删掉其他事实。

## 多 Writer / 多 Reviewer 的边界

默认只有一个 Writer 和一个 Reviewer，保证章节版本、口吻和证据链单一。需要多方案时，Coordinator 只能创建**互不重叠的候选分支**：例如开篇方向、章节卡方案或局部段落替换，每个分支必须绑定同一份 Context Packet、相同硬约束、明确范围和预算；候选正文不自动拼接、更不进入正史。用户或 Coordinator 选择一个分支后，才由单一 Writer 生成正式草稿。

需要第二意见时，多个 Reviewer 只能独立审同一正文哈希和同一 Context Packet；它们的分歧以结构化异议保存，由 Coordinator 汇总证据。任何一份“通过”都不能覆盖另一份有证据的硬冲突，最终仍由当前版本的门禁和用户验收决定。这样增加的是受控对照，不是让多个 Agent 自由改写同一章。

## 正史正文升级

旧项目若没有 SQLite 正文列，打开时只显示影响，不自动迁移。用户确认后，墨流先用 SQLite 备份 API 在 `.inkflow/backups/` 建立一致性备份，再以追加字段方式升级，并且只在 Markdown 与已存哈希一致时回填。无法验证的旧正文不会被猜测、不会被覆盖，会明确列出等待人工处理。

## 权限与费用

Coordinator 只能选择代码中已有的工作流，不能发明工具或扩权。PowerShell 默认关闭；用户在设置中了解影响并开启后，也只能以当前小说项目为工作目录。可选 NLI、裁判模型、BGE 语义模型和 reranker 都默认关闭，因此不会仅因升级而自动增加付费调用或下载本地模型。
